## Variables and signal naming

Every dashboard has `ds_metrics` (Prometheus/Mimir), `ds_logs` (Loki) and `ds_traces` (Tempo) datasource picker variables. Select the reviewed existing datasources on first load. No dashboard stores a datasource UID. The research observed `grafanacloud-prom`, `grafanacloud-logs` and `grafanacloud-traces`; those are examples for a later reviewer, not dependencies embedded in panels.

`namespace` defaults to `keyloop-scheduler`. `service` defaults to `api`, or `web-browser` on Frontend. Metric queries select `job="${namespace}/${service}"`, which is how OTLP translation builds `job` (`service.namespace/service.name`), so no lookup is needed. The variables do not filter `target_info` by `service_name` or `service_namespace`: by default the translation keeps only `job` and `instance` of the identifying resource attributes on `target_info`, and Mimir's `otel-keep-identifying-resource-attributes` is off by default. Environment is a multi-select query variable, `label_values(target_info{job="${namespace}/${service}"}, deployment_environment_name)`, default `Production`. Frontend discovers environments from the API's resource info because the browser emits traces only, with an `api_service=api` constant for end-to-end searches. API health adds a route picker; Notifications adds the bounded notification kind enum. Dashboard links preserve environment, namespace, datasource selection and time while allowing each destination's service default. Adjust `service` when reviewing a renamed service.

Mimir translation is expected to replace dots with underscores, add `_milliseconds` for `ms`, `_seconds` for `s`, `_total` for monotonic counters, and `_bucket`/`_sum`/`_count` for explicit histograms. Braced count units have no suffix. Point labels become `dealership_id`, `http_route`, etc. Resource attributes supply `job`, `instance`, `service_name`, `service_namespace`, `service_version` and `deployment_environment_name`. `target_info` is generated by resource translation. Tempo attributes keep dots, and every trace/log query filters the selected namespace, service and environment. See [Grafana OTLP format](https://grafana.com/docs/grafana-cloud/send-data/otlp/otlp-format-considerations/).

All panels have descriptions and units; rates use at least a 1-minute step and `$__rate_interval`. Ratios stay undefined at zero traffic. Histograms are approximate until G1 improves bucket boundaries at 150/300 ms. No Npgsql metric name is guessed before discovery.

OTel creates a counter series on its first `Add`, so a series' first exported sample already holds its first event, and `increase()` alone reads 0 for it. The code only ever adds 1, so plain `increase()` misses the first deadlock, backstop, dead letter or failed poll of a process. Those queries (all must-be-zero rules and stats, and the readiness rule and its evidence panel) therefore use one form, `validate.born_aware()`: `increase()` for series present one window ago, plus `max_over_time()` for series first seen inside the window. `validation/behaviour-tests.yaml` proves it with promtool. Never-fired counters export no series, so must-be-zero stats and rules end in `or vector(0)` (`or on() vector(0)` when grouped). A zero fallback does not prove that telemetry is flowing. Two gaps remain, listed in the Booking deadlocks runbook: a process that dies before its first export, and a restart that reuses the `instance` label within about 15 minutes. The planned Cloudflare `instance` is the Durable Object id, which every container restart reuses. Recording `Add(0)` for each must-be-zero series when the process starts would close the restart gap; that is an API code change, not part of this deliverable. Other range counts (bookings confirmed, sends, retries) still miss a series' first sample and say so in their descriptions.

## Offline validation

Prerequisites: Python 3.10 or later, the dependencies below, gcx 1.3.0, and `promtool` from Prometheus 3.x (checked with 3.5.0). `GCX`, `PROMTOOL` and `GRAFANA_VALIDATION_PYTHON` override the commands; `PROMTOOL` may be a container command that mounts this repository at the same path, for example `PROMTOOL="docker run --rm -v $PWD:$PWD --entrypoint promtool prom/prometheus:v3.5.0"` from the repository root. A missing tool fails the run. Dependency installation downloads packages, but all subsequent validation is local and needs no Grafana authentication. Use a venv inside this tree; generated files are ignored.

```bash
python3 -m venv observability/grafana/.venv
observability/grafana/.venv/bin/python -m pip install --no-cache-dir \
  -r observability/grafana/validation/requirements.txt

# Strict check against the code and ARCHITECTURE in this tree:
scripts/validate-dashboards.sh
```

The wrapper runs these stages, and any failure exits non-zero:

1. Self-tests (`validation/test_validate.py`): each guard below rejects the defect it exists for.
2. Structure: YAML with duplicate-key rejection, the local JSON Schema, the folder annotation, layout, links, datasource variables and the `job`/environment scope of every selector in all 48 panels.
3. Alert contract: each of the eight rules' threshold, pending period, query window, severity, evaluation settings, and dashboard/runbook links are pinned in `validate.py` (`ALERTS`), from plan section 5.2 and ARCHITECTURE section 12.3. Changing one is a deliberate edit there.
4. Metric and label inventory over panel, variable and alert queries: every series exists in `validation/metrics.json`; every matcher and `by`/`without`/`on`/`ignoring` label is a catalogued point label or a promoted resource label of the queried series; every `histogram_quantile` aggregates `sum by (le, ...)` over a `_bucket` series. Custom instrument kinds and units are checked against the generic and non-generic `Create...` declarations in every telemetry folder listed in `validate.py` (`TELEMETRY`): Api `Common/Telemetry/SchedulerTelemetry.cs` for booking, availability and cancellation, and Infrastructure `Telemetry/InfrastructureTelemetry.cs` for notifications (ADR-025). A missing folder fails the check. Every custom instrument name must also appear in ARCHITECTURE section 12. Framework instruments are checked against ServiceDefaults' `AddAspNetCoreInstrumentation` registration and the built-in ASP.NET Core meter catalogue, with pinned upstream citations in `validation/metrics.json`; they are not application-created instruments. `target_info` is checked as an OTLP-generated resource series.
5. PromQL behaviour: `validation/behaviour-tests.yaml` scenarios run the committed counter queries in promtool, including each series' first export, new and reused `instance` labels, other environments and jobs, and per-label alert instances.
6. gcx lint, with no rule disabled. gcx 1.3.0 applies its dashboard rules (`target-valid-promql`, `panel-title-description`, `panel-units`) only to `dashboard.grafana.app/v1beta1`, so it lints temporary v1beta1 copies of the dashboards (the classic spec is identical) and a synthetic v1beta1 dashboard carrying every alert query. It lints the alert rules themselves, or the prepared files with `--alerts-dir`. A canary with one defect per rule must then fail every rule, so the gate cannot silently pass everything again.

`validation/resource.schema.json` is a project authoring contract for the fields used here, based on the classic dashboard model and [Grafana's AlertRule spec](https://github.com/grafana/grafana/blob/main/apps/alerting/rules/pkg/apis/alerting/v0alpha1/alertrule_spec_gen.go). It is not a downloaded stack schema and cannot prove compatibility with the future destination's alpha API, Loki/Tempo query execution, renderer or live labels.

Notifications are integrated, so the strict check reads every notification instrument from Infrastructure `InfrastructureTelemetry.cs`, including both G2 gauges, `scheduler.notifications.outbox_pending` (`{notification}`, `kind` label) and `scheduler.notifications.oldest_pending_age` (`s`). Their names match the integrated code and ARCHITECTURE. The pre-merge `--notification-source` and `--allow-planned-gauges` options are gone. The attempt-only age histogram and range counter approximation do not substitute for backlog gauges.

## Local alert preparation

Alert evaluation has no dashboard template-variable context. Source templates therefore use explicit `${METRICS_DATASOURCE_UID}`, `${ENVIRONMENT}`, `${API_JOB}`, `${ALERT_RECEIVER}` and `${RUNBOOK_BASE_URL}` placeholders. Materialize them locally after the stakeholder chooses the destination settings, then review those files. Do not push the source alert templates.

```bash
# These are reviewed non-secret settings. Substitute real choices locally.
observability/grafana/.venv/bin/python \
  observability/grafana/validation/prepare-alerts.py \
  --metrics-datasource-uid '<existing-mimir-uid>' \
  --environment Production \
  --api-job keyloop-scheduler/api \
  --receiver '<existing-reviewed-contact-point-name>' \
  --runbook-base-url 'https://<reviewed-host>/<published-path>/runbooks.md'

scripts/validate-dashboards.sh \
  --alerts-dir observability/grafana/.review/alertrules
```

The command makes eight local files in `.review/alertrules`, refuses to overwrite a previous review, rejects unresolved templates, and never calls Grafana. With `--alerts-dir`, the validator requires each prepared rule to equal its tested template apart from one consistent value per placeholder, and gcx lints the prepared files rather than the templates. Use a new `--output-dir` inside this tree for a changed review.

All rules evaluate each minute, use `noDataState: Ok` and `execErrState: Error`, and reference a dashboard/panel and runbook. Counter rules count a series' first export, as described above. The eight rule conditions are:

- HV competence: any first-export-aware increment of `scheduler_allocation_below_hv_minimum_total` pages immediately.

| Rule | Condition | Pending period |
| --- | --- | --- |
| Deadlocks | 10-minute increase > 0 | 0s |
| Constraint backstop | 10-minute increase by constraint > 0 | 0s |
| API 5xx | 10-minute ratio > 0.001, excluding health routes | 5m |
| Booking p95 | 5-minute p95 > 300 ms and throughput > 0.02/s | 5m |
| Outbox age | Oldest Pending gauge > 300 s | 10m |
| Dead letters | 15-minute increase by kind > 0 | 0s |
| Readiness | Observed `/health` or `/alive` non-2xx in 5 minutes | 0s |

Dead letters follow plan section 5.2 (ticket severity). Readiness is the rule the Task 23 scope added. It detects reported failed polls and cannot establish external availability. In the planned Cloudflare topology (edge code under `deploy/cloudflare`, integrated in `94bd27b`) the Worker answers public `/health` and `/alive` from static assets, and the Durable Object pings only `localhost/alive` while the container starts. Nothing calls `/health` on the container, and `/alive` does not touch the database, so as deployed this rule covers failed start pings only. Pointing that ping at `/health`, or adding another in-network poller, would make it a database readiness signal; that is an edge change. An idle container sleeps, so missing `target_info` is not an outage condition. An actual external uptime check is a separate decision because it wakes the container and incurs cost.
