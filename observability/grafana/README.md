Dashboards use the classic panel JSON model in YAML `dashboard.grafana.app/v1` resources. Folder placement is `metadata.annotations["grafana.app/folder"]`. Alert resources use `rules.alerting.grafana.app/v0alpha1`. Push only the explicit manifest directories, not this whole directory containing schemas, dependencies and helper files.

## Variables and signal naming

Every dashboard has `ds_metrics` (Prometheus/Mimir), `ds_logs` (Loki) and `ds_traces` (Tempo) datasource picker variables. Select the reviewed existing datasources on first load. No dashboard stores a datasource UID. The research observed `grafanacloud-prom`, `grafanacloud-logs` and `grafanacloud-traces`; those are examples for a later reviewer, not dependencies embedded in panels.

`namespace` defaults to `keyloop-scheduler`. `service` defaults to `api`, or `web-browser` on Frontend. API dashboards resolve a `job` from `target_info`, defaulting to `keyloop-scheduler/api`. Environment is a multi-select query variable, default `Production`. Frontend discovers environments from the API's resource info because the browser emits traces only, with an `api_service=api` constant for end-to-end searches. API health adds a route picker; Notifications adds the bounded Task 19 kind enum. Dashboard links preserve environment, namespace, datasource selection and time while allowing each destination's service default. Adjust both service and job when reviewing a renamed service.

Mimir translation is expected to replace dots with underscores, add `_milliseconds` for `ms`, `_seconds` for `s`, `_total` for monotonic counters, and `_bucket`/`_sum`/`_count` for explicit histograms. Braced count units have no suffix. Point labels become `dealership_id`, `http_route`, etc. Resource attributes supply `job`, `instance`, `service_name`, `service_namespace`, `service_version` and `deployment_environment_name`. `target_info` is generated by resource translation. Tempo attributes keep dots, and every trace/log query filters the selected namespace, service and environment. See [Grafana OTLP format](https://grafana.com/docs/grafana-cloud/send-data/otlp/otlp-format-considerations/).

All panels have descriptions and units; rates use at least a 1-minute step and `$__rate_interval`. Deadlocks and constraint backstop use `or vector(0)` because never-fired counters may not export a series. A zero fallback does not prove that telemetry is flowing. Ratios stay undefined at zero traffic. Histograms are approximate until G1 improves bucket boundaries at 150/300 ms. No Npgsql metric name is guessed before discovery.

## Offline validation

Prerequisites: Python 3.10 or later, the dependencies below, and gcx 1.3.0. Dependency installation downloads packages, but all subsequent validation is local and needs no Grafana authentication. Use a venv inside this tree; generated files are ignored.

```bash
python3 -m venv observability/grafana/.venv
observability/grafana/.venv/bin/python -m pip install --no-cache-dir \
  -r observability/grafana/validation/requirements.txt

# Strict check against code and SYSTEM_DESIGN in this tree after integration:
scripts/validate-dashboards.sh

# Before Task 19 is merged, read its source without writing or building there:
scripts/validate-dashboards.sh --notification-source ../wt-scheduler-notify

# Authoring review only: reports exactly the two missing G2 gauges as PENDING.
scripts/validate-dashboards.sh --notification-source ../wt-scheduler-notify \
  --allow-planned-gauges
```

The wrapper checks gcx help, runs all built-in linters without disabling rules, validates YAML with duplicate-key rejection and the local JSON Schema, checks all 48 panels for layout/links/variables, checks six alert expression graphs, and inventories metrics in panel, variable and alert queries. It verifies custom instrument kinds/units against `SchedulerTelemetry.cs` and core names against SYSTEM_DESIGN section 12. Framework instruments are verified against ServiceDefaults' `AddAspNetCoreInstrumentation` registration and the documented built-in ASP.NET Core meter catalogue, with pinned upstream source citations in `validation/metrics.json`. These built-ins are not application-created instruments. `target_info` is verified as an OTLP-generated resource series. Alert PromQL is also fed through gcx as a temporary local dashboard because the built-in PromQL rule checks dashboards only.

`validation/resource.schema.json` is a project authoring contract for the fields used here, based on the classic dashboard model and [Grafana's AlertRule spec](https://github.com/grafana/grafana/blob/main/apps/alerting/rules/pkg/apis/alerting/v0alpha1/alertrule_spec_gen.go). It is not a downloaded stack schema and cannot prove compatibility with the future destination's alpha API, Loki/Tempo query execution, renderer or live labels.

Strict mode currently fails: the local branch has no Task 19 instruments, and the read-only notification branch has no G2 gauges. The review flag allows only `scheduler.notifications.outbox_pending` (`{notification}`, expected kind label) and `scheduler.notifications.oldest_pending_age` (`s`). Their exact names are taken from Task 19's binding G2 brief, superseding the plan's older `outbox_oldest_pending_age` spelling. They remain visible as No data, with panel descriptions stating the missing instrumentation. The outbox-age alert uses the planned oldest-Pending gauge and remains ineffective until it exists. The attempt-only age histogram and range counter approximation do not substitute for backlog gauges.

## Local alert preparation

Alert evaluation has no dashboard template-variable context. Source templates therefore use explicit `${METRICS_DATASOURCE_UID}`, `${ENVIRONMENT}`, `${API_JOB}`, `${ALERT_RECEIVER}` and `${RUNBOOK_BASE_URL}` placeholders. Materialize them locally after the stakeholder chooses the destination settings, then review those files. Do not push the source alert templates.

```bash
# These are reviewed non-secret settings. Substitute real choices locally.
observability/grafana/.venv/bin/python \
  observability/grafana/validation/prepare-alerts.py \
  --metrics-datasource-uid '<existing-mimir-uid>' \
  --environment Production \
  --api-job keyloop-scheduler/api \
  --receiver '<existing-reviewed-contact-point-name>' \
  --runbook-base-url 'https://<reviewed-host>/<published-path>/runbooks.md'

scripts/validate-dashboards.sh \
  --alerts-dir observability/grafana/.review/alertrules
```

The command makes six local files in `.review/alertrules`, refuses to overwrite a previous review, rejects unresolved templates, and never calls Grafana. Before integration, the same validator requires `--notification-source`; the G2 review flag may be used for authoring but must not be treated as deployment acceptance. Use a new `--output-dir` inside this tree for a changed review. Compare the rendered manifests with `alertrules/` to confirm only the settings changed.

All rules evaluate each minute, use `noDataState: Ok` and `execErrState: Error`, and reference a dashboard/panel and runbook. The six rule conditions are:

| Rule | Condition | Pending period |
| --- | --- | --- |
| Deadlocks | 10-minute increase > 0 | 0s |
| Constraint backstop | 10-minute increase by constraint > 0 | 0s |
| API 5xx | 10-minute ratio > 0.001, excluding health routes | 5m |
| Booking p95 | 5-minute p95 > 300 ms and throughput > 0.02/s | 5m |
| Outbox age | Oldest Pending gauge > 300 s | 10m |
| Readiness | Observed `/health` or `/alive` non-2xx in 5 minutes | 0s |

The user's Task 23 scope selects readiness as the sixth rule, replacing the plan's dead-letter alert. Dead letters still have a must-be-zero panel. Readiness detects reported failed polls; it cannot establish external availability. An idle container sleeps, so missing `target_info` is not an outage condition. An actual external uptime check is a separate decision because it wakes the container and incurs cost.
