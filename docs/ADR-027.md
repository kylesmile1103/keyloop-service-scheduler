# ADR-027: Cloudflare Access identity with API role authorization

Status: accepted API/product decisions, 2026-10-12. Deployment settings and the live browser rehearsal await stakeholder confirmation. Supersedes the deferred seam in A-10 / ADR-010. The frontend sign-in controls (Task 27b) are described under "Frontend" below.

The public board, calendar, catalogue and availability remain readable without login. Booking, cancellation and both intake triage writes (the Clef evaluation and the photo upload) require Admin or ServiceAdvisor, while triage status stays public; appointment details require any of Admin, ServiceAdvisor or Viewer. The demo reseed requires Admin and its existing key. Roles apply across dealerships in this take-home; tenant/dealership membership is a separate future policy.

## Access research and login path

Research checked current official documentation on 2026-10-12:

- [Authorization cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/): the application token is on the protected hostname; disabling the Cookie Path Attribute removes application-path scoping. Choose one self-hosted application at `keyloop.kylesmile.me/auth/*`, disable that attribute, enable HttpOnly, and select SameSite Lax for the same-origin app. Inference: the browser can then send its hostname cookie to `/api/v1/*`. This must be checked during the deploy browser rehearsal. The application cookie lifetime follows policy duration, then application duration, with a 24-hour fallback; choose a shorter explicit duration.
- [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/): validate the RS256 signature using the team's `/cdn-cgi/access/certs`, issuer and application AUD. Keys rotate every six weeks by default with seven days of overlap. Prefer the assertion header where Access supplies it. The documentation does not guarantee header injection on unprotected paths, so the API also validates the cookie. A header that is present takes precedence, including invalid or multiple assertions.
- [Application paths](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/app-paths/) and [policy selectors](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/): protection selects hostnames/paths; these controls do not supply an HTTP-method selector. Keep the API paths public at Access and enforce methods/roles in ASP.NET authorization. `/auth/*` does not include the bare `/auth` parent; `/auth/login` is inside the protected wildcard. Query strings are not application selectors.
- [Session management](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/): navigate to the hostname's `/cdn-cgi/access/logout` to clear its cookie. Cloudflare logout affects sessions across applications, not just this app. Access itself rejects revoked tokens shortly afterwards. Our offline validator on unprotected paths cannot observe session revocation; a copied JWT can remain usable until its expiry plus clock skew. Logout immediately removes this browser's API identity when its cookie is cleared. A one-hour application/policy duration is proposed for ratification.
- [Identity providers](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/) and [one-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/): use hosted email PIN for approved reviewers, with Google/GitHub optional. Restrict the Allow policy to approved emails or domains; choosing PIN as an unrestricted Include rule would admit arbitrary email identities. No application-owned login screen or password store is needed.
- [Rule groups](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/groups/) are reusable Access policy selectors, distinct from IdP groups. [Application tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/) only include IdP groups when explicitly selected as custom SAML/OIDC attributes, under `custom`; large custom values can be trimmed. Use configured email membership for API roles. Group mapping would require a separate validated integration and cannot assume Access rule-group names appear in a JWT.

`GET /auth/login?returnTo=<local path>` requires verified identity and redirects locally after Access's hosted flow. The API rejects external, protocol-relative, backslash and control-character return targets and marks the redirect no-store. API 401s link to login with `/` as the return target, avoiding navigation to a POST-only API URL. The web app never follows a `loginUrl` it is given: it navigates to `/auth/login` on its own origin with `returnTo` set to the current local page and search, checked as the API checks it (Task 27b, "Frontend" below). `/api/v1/me` provides the same login URL and the hostname logout URL.

If the browser rehearsal cannot retain a hostname-wide application cookie, stop that deployment and propose a protected API application with separate public read paths. Do not introduce a Bypass policy that silently drops identity on writes, or claim the assertion header exists off the protected paths without evidence.

## API implementation

`Auth:Mode` is CloudflareAccess by default (UAT, Production and Demo). Development is allowed only in Development; None is allowed only in SystemTest and still leaves protected routes unauthorized. A test-only handler, registered in the test assembly, selects an identity using `X-Test-Role`. The deployed handler never reads that header or trusts a bearer header, email header, token roles or custom groups.

A small ASP.NET authentication handler delegates JOSE validation to Microsoft's `JsonWebTokenHandler`. It explicitly requires RS256, a signing key, the exact HTTPS team issuer, one configured application audience, expiry and not-before bounds. An injected TimeProvider implements a 30-second default skew, configurable only up to one minute. Only verified human email/name/subject claims enter the principal. Machine tokens without an email are rejected. Validation exceptions never enter application logs; authentication failures carry fixed messages.

JWKS JSON uses source-generated metadata, no runtime JSON reflection or OpenID discovery. A singleton key cache refreshes hourly or for unknown key ids, with a 30-second refresh floor and one fetch at a time. HTTP responses are bounded to 64 KiB, time out after five seconds, and do not follow redirects. An expired cache fails closed when refresh fails; unexpired known keys remain usable during the cache interval. Newly rotated keys can require up to 30 seconds before refresh when the previous fetch was recent. The documented overlap makes that interval practical.

Authorization is deny by default. Public operations, `/api/v1/me`, health probes and the OpenAPI/Scalar reference declare `AllowAnonymous`; protected ones name their policy. The fallback policy makes any other mapped route Admin-only, while requests that match no route, or a mapped path with the wrong method, keep routing's 404/405. A test enumerates every mapped route, including those excluded from OpenAPI, against its expected access, and the OpenAPI transformer documents an operation as public only when it is explicitly anonymous.

`IClaimsTransformation` maps case-insensitive bare emails or exact `@domain` entries from `Auth:Roles:Admin`, `ServiceAdvisor`, `Viewer`. Domains do not include subdomains. Membership in multiple lists grants multiple roles. Unknown authenticated users receive no role and 403 on protected operations. Startup validation uses generated binding and `[OptionsValidator]`, plus an explicitly registered environment validator, before database work; diagnostics identify settings without echoing personal data.

Public schedule and range responses keep their schema. One shared policy, `PersonalData.ForCaller`, decides what each caller sees. Callers without an authenticated API role get one upper-case initial per whitespace-separated name part (from its first letter), the domain VIN mask `Vin.Masked` that logs and events already use (`***********123456`), and the registration fully masked as `*******`, whatever the plate. Registrations are masked because a plate linkable to a person is personal data (ICO guidance), and completely because the last three letters of a current UK plate are its most distinctive part; the fixed width also hides the plate's length. Any API role gets the full name, VIN and registration. Workshop resources remain visible; contact email/phone and free text are only in the protected appointment detail. API responses are no-store. Audit uses `user:<verified-email>` or `anonymous:<ip>` (emails over the RFC 5321 limit of 254 characters are rejected as identities, and the audit column holds 300 characters); rate limiting uses that authenticated email, case normalized, or the client IP. Neither identity value is added to log messages or metric tags.

OpenAPI describes alternative Access-header and cookie security schemes, optional authentication on public operations, 401 `unauthenticated` with `loginUrl`, 403 `forbidden`, masking, and `GetCurrentUser`. HTTP and problem DTOs are explicitly registered in the source-generated context. No new reflection discovery is introduced.

The AppHost run profile passes Development with `admin@keyloop.test` / Admin by default, and optional `Parameters:auth-development-email` and comma-separated `Parameters:auth-development-roles`. An empty role string selects anonymous. Publish mode requires `access-team-domain` and `access-audience`; it cannot inherit a Development identity. Local Compose readers remain anonymous unless a compatible Access front door is supplied for authenticated use.

## Cross-site request forgery

Writes authenticated by the hostname cookie need a forgery defense, because the browser attaches `CF_Authorization` to any request to the hostname. Cloudflare's documented default SameSite value for the application cookie is None, so the operator checklist selects SameSite Lax. The API adds two properties that hold whatever the cookie setting: write endpoints bind JSON bodies only, so the simple content types a cross-site form or no-CORS fetch can send (`text/plain`, form-urlencoded, multipart) get `415` before any handler runs (an integration test pins this for booking, cancellation, triage evaluation and photo upload); and CORS is default-deny and never allows credentials, so a cross-origin JSON request cannot carry the cookie. The demo reseed additionally requires its custom key header. A future form-encoded endpoint or credentialed CORS would need an anti-forgery token.

The [Access binding cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/) (`CF_Binding`) does not help here. Cloudflare strips it at its network and never forwards it to the origin, and checks it only for requests that Access itself protects. The public `/api/v1/*` paths are not behind Access, so the API validates `CF_Authorization` without any binding check whether or not the operator enables it.

## Frontend (Task 27b)

The web app reads `GET /api/v1/me` once and shares it (fresh for a minute, read again when the window regains focus) and mirrors the policies before any request, so a request the API would refuse is not sent: a visitor who is not signed in gets a sign-in prompt before the booking dialog opens (and a sign-in panel in the details sheet, without requesting the record); a Viewer or an unassigned account sees each write unavailable with the reason; the Resources area needs a role (the 401 page in place for a visitor, the 403 page without a role). Signing in is a top-level navigation to `/auth/login` on the app's own origin with `returnTo` the current local path and search, or `/` when that is not a local path (one leading `/`, not `//`, no backslash, no control character); the `loginUrl` of `/me` or a `401` problem is never followed, so no answer can send the browser to another origin or path. Signing out is a navigation to `/cdn-cgi/access/logout`, offered when `/me` gives a `logoutUrl`. The app has no password form and never reads, stores or forwards a token or requests the login path by script.

The API stays the judge. A `401` or `403` the UI did not foresee (a session that ended, a role removed) is answered in one place: "Your session has ended" with Sign in (the same `/auth/login` address, never the problem's `loginUrl`), or "Your role doesn't allow that"; `/me` is then read again. When `/me` names another caller, every cached read but the caller-independent reference data is cleared and read again, and settled mutations are dropped, so a full name, VIN, plate or contact detail read as one caller never shows to the next.

Decisions: a visitor is prompted before the booking dialog opens rather than keeping a draft through the sign-in, because the draft holds a customer's details and would have to survive a full-page navigation in browser storage; when the identity changes while the dialog is open, what was typed stays on screen with the reason and is not stored. The Development identity is configuration, so the Vite dev server (which only ever fronts it) offers "How to sign in" (Settings > Account, naming the settings) and no Sign out: there `/auth/login` answers a signed-out caller with a 401 problem and nothing serves the Access logout. `vite.config.ts` compiles that choice into the dev server only; every build links to Access. A production build served against a Development API (`vite preview`) would therefore show Access links that the Development API cannot honour; that pairing is not a supported deployment.

## Rejected alternatives

- Edge-only trust: headers and direct-origin reachability can be forged or misconfigured; the API must validate signature, audience and expiry itself.
- Entra ID or Auth0 as a separate application identity layer: duplicates the selected Access front door and its hosted reviewer login. They remain possible Access identity providers.
- ASP.NET Identity/local accounts: password reset, account storage and login UI add scope unrelated to the evaluated scheduler.
- HTTP-method Access policies: not supported by the cited path/selector model; the API owns the route/method matrix.
- Protecting every API path with Access: blocks anonymous viewing and returns hosted login redirects to API clients. Separate public paths are a contingency if the cookie rehearsal fails.
- API authorization from Access rule-group names or presumed token groups: group types differ and custom claims are optional/trimmable; explicit email lists meet the approved requirements.

## Operator boundary

The [edge deployment checklist](../deploy/cloudflare/README.md#access-login-and-api-roles-task-27) lists the team, application, paths, policies, IdPs, AUD tags, private role lists and browser checks. No account resources were created and no live token was used in Task 27. Role lists contain personal data and must be supplied outside the repository; changing a container's start-time auth settings requires restarting it. Offline revocation limits, session duration, role lists and optional IdPs require deploy-time ratification.
