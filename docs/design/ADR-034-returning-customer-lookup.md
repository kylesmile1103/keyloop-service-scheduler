# ADR-034: Returning customers from booking history

Accepted 2026-10-13, Task 39A.

Workshop staff book on behalf of customers. Customer details already live on each appointment; the signed-in staff member's profile cannot supply them. The stakeholder chose search and selection of earlier bookings over customer self-service or a staff-details shortcut.

Derive returning customers from this dealership's appointments, across all statuses. Group by case-insensitive email and VIN. A match on any booking identifies the pair; its latest start UTC (then id descending) supplies name, email, phone, VIN, registration, make and model. Count all bookings of the pair and return at most eight pairs, latest first. Do not create a customer master, customer account or stable customer id. Email changes deliberately create a separate pair; this is a history projection, not identity resolution.

Expose `POST /api/v1/dealerships/{dealershipId}/customer-lookups`, operation `FindReturningCustomers`, body `{ query }`, to `BookingsWrite` only. Reuse the booking rate limit and no-store middleware. Search input is personal data and remains transient body/SQL-parameter data. Event 1500 records only kind and result count. No profile, provenance, requirements, notes or other booking fields leave the projection.

The migration creates four dealership-leading B-tree expression indexes for email, normalized registration, digits-only phone and reversed phone, a GIN array expression index for every name-word prefix of length at least three, and a dealership/email/VIN/start/id B-tree for latest fields and visit counts. The name is bounded to 120 characters, bounding prefix fan-out. The immutable SQL function uses only pg_catalog built-ins with a fixed search path and invoker privileges. No pg_trgm, btree_gin or other extension is required. PostgreSQL 17 provides these index methods on Neon as well as locally; the runtime role needs its existing schema USAGE, table SELECT and PostgreSQL's default PUBLIC function EXECUTE, never CREATE or extension installation. An installation that revokes default function EXECUTE must explicitly grant execution on this function to its runtime role. The migration owner performs DDL; the existing runtime-role script does not revoke function execution.

Prefix matching is literal and case-insensitive for email/name. Phone matches either end after digit normalization; registration removes whitespace and uppercases. Names match the beginning of any whitespace-separated word, preserving punctuation without stemming or stop-word removal. Broad prefixes can match many pairs and still require aggregation before the eight-result limit; the EXPLAIN proof uses selective queries with planner defaults on 100,000 appointments and does not claim every prefix is constant-cost.

Alternatives rejected: a customer master (ownership, deduplication and lifecycle beyond this intake convenience), substring/fuzzy search with pg_trgm (additional extension and looser match semantics), full-text lexemes (punctuation tokenization and stop words change literal word-prefix semantics), scanning appointment history in application memory (unbounded work and personal-data materialization).

PostgreSQL references: [expression indexes](https://www.postgresql.org/docs/17/indexes-expressional.html), [pattern operator classes](https://www.postgresql.org/docs/17/indexes-opclass.html), and [GIN array operators](https://www.postgresql.org/docs/17/gin.html). These justify the index mechanisms; the local EXPLAIN proof records the actual selected plans.
