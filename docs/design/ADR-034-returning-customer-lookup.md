# ADR-034: Returning customers from booking history

Accepted 2026-10-13, Task 39A.

Amended 2026-10-13, Task 39C: multi-word names and UK/German national and international phones.

Workshop staff book on behalf of customers. Customer details already live on each appointment; the signed-in staff member's profile cannot supply them. The stakeholder chose search and selection of earlier bookings over customer self-service or a staff-details shortcut.

Derive returning customers from this dealership's appointments, across all statuses. Group by case-insensitive email and VIN. A match on any booking identifies the pair; its latest start UTC (then id descending) supplies name, email, phone, VIN, registration, make and model. Count all bookings of the pair and return at most eight pairs, latest first. Do not create a customer master, customer account or stable customer id. Email changes deliberately create a separate pair; this is a history projection, not identity resolution.

Expose `POST /api/v1/dealerships/{dealershipId}/customer-lookups`, operation `FindReturningCustomers`, body `{ query }`, to `BookingsWrite` only. Reuse the booking rate limit and no-store middleware. Search input is personal data and remains transient body/SQL-parameter data. Event 1500 records only kind and result count. No profile, provenance, requirements, notes or other booking fields leave the projection.

The migration creates four dealership-leading B-tree expression indexes for email, normalized registration, digits-only phone and reversed phone, a GIN array expression index for every name-word prefix of length at least three, and a dealership/email/VIN/start/id B-tree for latest fields and visit counts. The name is bounded to 120 characters, bounding prefix fan-out. The immutable SQL function uses only pg_catalog built-ins with a fixed search path and invoker privileges. No pg_trgm, btree_gin or other extension is required. PostgreSQL 17 provides these index methods on Neon as well as locally; the runtime role needs its existing schema USAGE, table SELECT and PostgreSQL's default PUBLIC function EXECUTE, never CREATE or extension installation. An installation that revokes default function EXECUTE must explicitly grant execution on this function to its runtime role. The migration owner performs DDL; the existing runtime-role script does not revoke function execution.

Prefix matching is literal and case-insensitive for email/name. Phone matches either end after digit normalization; registration removes whitespace and uppercases. Names match the beginning of any whitespace-separated word, preserving punctuation without stemming or stop-word removal. Broad prefixes can match many pairs and still require aggregation before the eight-result limit; the EXPLAIN proof uses selective queries with planner defaults on 100,000 appointments and does not claim every prefix is constant-cost.

For names, split the trimmed query on whitespace and ignore words shorter than three characters. Every remaining word must be a case-insensitive prefix of some word of the same booking's name, in any order: `grace hop` and `Hopper Grace` match `Grace Hopper`. Multiple prefixes may match the same name word; duplicate words add no requirement. If no eligible word remains, omit the name branch entirely, because containment of an empty array would match everyone. Single-word behavior remains unchanged. Registration still uses the entire query with whitespace removed. Bind the words as a text array and lowercase them in PostgreSQL, using the same casing rules as the existing name-prefix function. GIN array containment (`@>`) already expresses this conjunction, so the function and name index need no migration. Words from different historic bookings cannot combine to satisfy a name query; once one booking matches, the latest fields and all visits of its pair are projected as before.

For phones, `public.customer_lookup_phone_key(text)` first removes formatting while retaining ASCII digits and `+`. It strips a leading `+44` or `+49`, a leading `0044` or `0049`, or one leading national trunk `0` when it is not followed by another `0`; then it keeps only ASCII digits. Thus `+44 (7700) 900-123`, `0044 7700 900123` and `07700 900123` share `7700900123`; `+49 (151) 2345-6789`, `0049 151 23456789` and `0151 23456789` share `15123456789`. The identical function normalizes the stored index value and the bound query, preventing application/database drift. Normalized matching needs at least six significant query digits and supports a forward prefix for explicit national/international input and a reversed prefix for a suffix. Bare digits keep the earlier digit-only forward/suffix behavior: `447700` still matches a stored `+44` prefix and `900123` remains a suffix; `770090` remains a nonmatching middle fragment of `+44 7700 900123`. Normalized forward matching requires the key to differ from the raw query digits, so it does not broaden that last case. The original phone classifier is unchanged and still needs at least six ASCII digits, more digits than formatting characters, and only whitespace, `+`, brackets or hyphens otherwise. The legacy branches retain that six-raw-digit floor, including country-inclusive partial prefixes.

This is a bounded lookup rule for the UK and Germany, not phone validation or global identity resolution. Unmarked `44`/`49` are not guessed as country codes. Explicit international codes for other countries are retained as digits (`+33` and `0033` remain distinct keys); their national/international equivalence is not promised. One trunk zero is removed without a country field, so equal significant numbers across countries can collide in this dealership-scoped convenience search. Extensions, optional trunk zeros inside international notation such as `+44 (0)`, malformed numbers and other countries' trunk rules are not interpreted. The API contract, validation, result limits, authorization, privacy and problem responses stay the same; generated documentation changes only descriptions.

Migration `20261013091600_CustomerLookupPhoneNormalization` adds the immutable, strict, parallel-safe SQL function with a fixed `pg_catalog` search path and invoker privileges, plus dealership-leading B-tree `text_pattern_ops` indexes `ix_appointments_lookup_phone_key` and `ix_appointments_lookup_phone_key_reverse` on the key and its reverse. This is an additive replacement for the normalization path: the six Task 39A indexes and name function remain byte-for-byte unchanged, including the two raw-digit phone indexes used by the previous API and the legacy partial-query branches. Apply this migration before deploying the new API; the previous API's SQL remains correct and indexed after migration, with no dependency on the new function. Down removes only the new indexes and function; roll the API back first. Ordinary transactional CREATE INDEX may briefly wait for or block writes while building; no zero-downtime DDL claim is made. Keeping both phone index pairs adds storage and booking-write maintenance. No extension or new runtime DDL grant is needed; installations that revoke default PUBLIC function EXECUTE must grant it on the new function as for the existing name function. Integration tests verify upgrading populated history, old SQL before/after upgrade and rollback, empty-database migration, runtime grants and model parity. The Task 39C EXPLAIN evidence covers both name orders and national/international phone branches on 100,000 synthetic history rows with planner defaults.

Alternatives rejected: a customer master (ownership, deduplication and lifecycle beyond this intake convenience), substring/fuzzy search with pg_trgm (additional extension and looser match semantics), full-text lexemes (punctuation tokenization and stop words change literal word-prefix semantics), scanning appointment history in application memory (unbounded work and personal-data materialization).

PostgreSQL references: [expression indexes](https://www.postgresql.org/docs/17/indexes-expressional.html), [pattern operator classes](https://www.postgresql.org/docs/17/indexes-opclass.html), and [GIN array operators](https://www.postgresql.org/docs/17/gin.html). These justify the index mechanisms; the local EXPLAIN proof records the actual selected plans.
