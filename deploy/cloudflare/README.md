# Keyloop Cloudflare edge

This project serves the scheduler SPA and routes its API calls to a sleeping .NET Container on `keyloop.kylesmile.me`. It also owns the private email relay, an optional browser OTLP trace relay and the optional API telemetry export to Grafana Cloud. Deployment happens later with the stakeholder.

## Local verification

Use Node 22.18 or later within Node 22. The dependencies are pinned in `package-lock.json`, including project-local `cf` and Wrangler. These commands need no Cloudflare account, database, Docker daemon, email destination or Grafana account:

```sh
cd deploy/cloudflare
source ~/.nvm/nvm.sh
nvm exec 22 npm ci --cache ./build/npm-cache --no-audit --no-fund
nvm exec 22 npm run typecheck
nvm exec 22 npm test
nvm exec 22 npm run validate:build
nvm exec 22 npm run validate:build:integrations
```

If no sufficiently recent Node 22 is installed, `nvm install 22` installs it; keep the user's default alias unchanged. Always use the selected version for this project's commands.

`typecheck` first generates Cloudflare runtime and binding types locally. The build validations invoke **only `cf build`**, use dummy resource identifiers and separate fixture assets, disable CLI telemetry, isolate CLI state under this project's ignored directories, and check the emitted routing, bindings and container metadata. The second build includes the optional REST-email, browser-OTLP, API-telemetry and triage Secrets Store bindings without reading their values. Neither command assembles or overwrites a real SPA build.

Vitest runs unit tests and actual Static Assets routing in Miniflare. Global network fetches are denied by default; provider responses are explicit fakes. The Miniflare test uses compatibility date `2026-10-11` because its runtime rejects the next UTC date on this machine; the deployment config uses `2026-10-12`. Container lifecycle tests run the real `@cloudflare/containers` class against a fake container runtime (`cloudflare:workers` is aliased to a stub in `vitest.config.ts`), covering the 60-second readiness window for every request during a cold start, coalesced starts, restart configuration and the configuration restarts described under [Configuration changes](#configuration-changes-and-container-restarts); a deploy is modelled as a new Durable Object instance over the same storage and running container. Production egress, placement, real cold-start time and binding access remain deployment checks. `validate:build` also confirms that an invalid setting fails `cf build`.

## Assemble the real SPA

Build `src/Keyloop.ServiceScheduler.Web` with its own documented frontend commands first. From this edge directory, `nvm exec 22 npm run assemble` copies that project's `dist/` into `build/assets/`, adds the [static API reference](#static-api-reference) and `public/_headers`. It leaves the frontend output untouched, and it refuses a missing `dist/index.html` or a Scalar install that differs from the pinned version before replacing a prior assembly.

`wrangler.config.ts` is the bundler configuration consumed by `cf`; `cloudflare.config.ts` is the deployment source of truth. Do not add a competing `wrangler.jsonc` unless replacing the cf beta integration deliberately. A local build of the real assembly uses `nvm exec 22 npm run build` with the non-secret resource identifiers below set. Its wrapper disables CLI telemetry and runs only `cf build`. This build consumes an existing API image reference, so it does not build or publish an image.

## Configuration contract

Configure these environment variables when evaluating `cloudflare.config.ts`. They are resource identifiers and policy settings, never credential values. Access role lists contain personal data and must be supplied privately outside source control. `src/settings.ts` validates them during evaluation, so `cf build` fails on an unknown transport, REST without a 32-character hexadecimal account ID, an enabled OTLP relay or API telemetry export without a gateway endpoint, enabled API telemetry without a numeric Grafana instance ID, a switch other than `true` or `false`, or an allowlist or cap the container start would refuse. An empty value means the default. Because `cf` evaluates the config with Node's type stripping, modules under `src/` import each other with explicit `.ts` specifiers.

| Variable | Default / meaning |
| --- | --- |
| `KEYLOOP_SECRETS_STORE_ID` | Required existing store ID |
| `KEYLOOP_API_IMAGE` | Required existing registry image reference, immutable SHA tag recommended. Also bound to the Worker as text `API_IMAGE`, so a new image restarts the container with the current configuration |
| `KEYLOOP_ACCESS_TEAM_DOMAIN` | Required canonical `https://<team>.cloudflareaccess.com` issuer |
| `KEYLOOP_ACCESS_AUDIENCE` | Required comma-separated application AUD tags, case preserved |
| `KEYLOOP_ACCESS_ADMIN` | Empty; comma-separated exact emails or `@domain` role members, supplied outside the repository |
| `KEYLOOP_ACCESS_SERVICE_ADVISOR` | Same, for booking/cancel/triage operators |
| `KEYLOOP_ACCESS_VIEWER` | Same, for authenticated full reads and appointment details |
| `KEYLOOP_NOTIFICATIONS_ENABLED` | `false`; passed to the API at container start. `false` selects the API provider `None`; `true` selects the reserved `Cloudflare` provider, which the API refuses at startup until `RelayEmailSender` exists |
| `KEYLOOP_EMAIL_SENDING_ENABLED` | `false`; independent Worker kill switch |
| `KEYLOOP_EMAIL_TRANSPORT` | `binding`, or explicit `rest` fallback |
| `KEYLOOP_EMAIL_ACCOUNT_ID` | Existing account ID, needed for REST only |
| `KEYLOOP_EMAIL_ALLOWED_ADDRESSES` | Empty; comma-separated approved bare mailboxes |
| `KEYLOOP_EMAIL_ALLOWED_DOMAINS` | Empty; comma-separated exact domains, no wildcard or subdomain expansion |
| `KEYLOOP_EMAIL_MAX_PER_RECIPIENT_PER_DAY` | `10`, valid range 1-1000, enforced by the .NET dispatcher |
| `KEYLOOP_EMAIL_MAX_PER_DAY` | `100`, valid range 1-10000; reduce below the actual account quota |
| `KEYLOOP_OTLP_RELAY_ENABLED` | `false`; binds the browser credential only when `true` |
| `KEYLOOP_GRAFANA_OTLP_ENDPOINT` | Empty; `https://otlp-gateway-<region>.grafana.net/otlp`, without a trailing slash. Shared by the browser relay and API telemetry; required by whichever is enabled |
| `KEYLOOP_API_OTLP_ENABLED` | `false`; `true` binds `keyloop_prod_api_otlp_token` and passes the API its OTLP settings at container start ([Optional API telemetry](#optional-api-telemetry)) |
| `KEYLOOP_GRAFANA_INSTANCE_ID` | Empty; the Grafana Cloud stack's numeric instance ID (digits only, the Basic-auth user), required when API telemetry is enabled |
| `KEYLOOP_VEHICLE_AWARE_REQUIREMENTS` | `false`; `true` passes `Scheduling__VehicleAwareRequirements=true` at container start, this deployment's explicit override of the API's Production default (`appsettings.Production.json` keeps `false`). `false` passes nothing. See [Vehicle-aware booking](#vehicle-aware-booking) |

The store contains `keyloop_prod_db_url`, a direct (not `-pooler`) Neon TLS connection string for the runtime DML role in Npgsql keyword form (`Host=...;Port=5432;Database=...;Username=scheduler_app;Password=...;SSL Mode=VerifyFull;Channel Binding=Require`), not the `postgresql://` URI Neon shows by default, which the API refuses at startup. REST selection additionally binds `keyloop_prod_email_api_token`; browser relay enablement binds `grafana-otlp-basic-browser`, the base64 encoding of `instance-id:token`; API telemetry binds `keyloop_prod_api_otlp_token`, the Grafana access-policy token itself (not base64). The email and browser-relay credentials stay in the Worker; the triage and API telemetry tokens, like the DB credential, reach the container only in its start environment. Missing DB credentials prevent startup with a sanitised error. The container receives its whole configuration, secrets included, only when it starts; [Configuration changes](#configuration-changes-and-container-restarts) describes how a change reaches a running container.

Only approved recipients can be sent mail. Reserved example/test/invalid/localhost domains are always refused, even if allowlisted. The sender is fixed to `notifications@keyloop.kylesmile.me` and no reply-to is accepted. `test/fixtures/email-relay-request.json` is the JSON contract fixture for the .NET sender's parity test. The relay returns 200 whenever the provider accepted the message, with `messageId` when it is known. An acceptance it cannot fully confirm (a REST 2xx without the recipient echoed as delivered or queued, or a binding result without a message ID) is still 200 and logs `EmailAcceptedUnconfirmed` with the notification ID only, because neither transport has an idempotency key and a retry could duplicate the email. It returns 400 for malformed requests, 422 for permanent refusal, and 503 with `retryable=true` when the provider did not accept the message or the outcome is unknown, such as a timeout. There is no automatic fallback resend.

`/api`, `/api/*` and `/auth/*` reach the named `api` Durable Object with the `weur` hint. The Worker replaces client forwarding headers before proxying and preserves the Access assertion and `CF_Authorization` cookie unchanged. It does not decide API roles; the container validates the JWT itself. `/otlp/v1/traces` accepts POST JSON/protobuf, applies fetch-site/origin checks and a 256 KiB streamed size cap, and limits clients to 120/min. `/otlp` and other OTLP paths return JSON 404. Cloudflare owns the reserved `/cdn-cgi/access/logout` before Worker routing; verify it clears the hostname cookie at deploy. Every other ordinary path uses Static Assets: `/scalar/v1` is the [static API reference](#static-api-reference) and `/openapi/v1.json` the committed contract, both public documentation; everything else, including `/health`, `/alive` and bare `/scalar`, gets the SPA fallback. None of these paths reaches the API, so they never expose API internals. `public/_headers` sends host-only HSTS (`max-age=31536000`, no `includeSubDomains` or `preload`) from the first deploy, as decision 9 accepts. This deliberately departs from proposal 4.6, which adds HSTS only after HTTPS enforcement works: the redirect can only be verified once the Custom Domain exists, and browsers record HSTS only from a valid HTTPS response (RFC 6797 section 8.1), so it cannot take effect before the certificate works. To follow the proposal's order instead, remove that line before step 3 and restore it after step 5. The trust contract and deployment profile are in [ARCHITECTURE](../../docs/ARCHITECTURE.md#114-cloudflare-edge-boundary-and-credentials).

## Static API reference

The board's sidebar links "API reference" to `/scalar/v1`. Locally the Vite proxy sends that path to the API, which maps Scalar and `/openapi/v1.json` outside Production (ADR-018; unchanged). The deployed API runs as Production and maps neither, so the edge publishes a static reference at the same paths instead: `api-reference/v1.html` becomes `/scalar/v1` (Static Assets serve `scalar/v1.html` there and redirect `/scalar/v1/` and `/scalar/v1.html` to it), and `/openapi/v1.json` is a copy of the committed `contracts/openapi/v1.json`, the build-time contract every API build writes and `OpenApiContractTests` keeps equal to the runtime document. It is public documentation of the public API: the routes, schemas and problem types, with no servers, settings or secrets. It does not reveal the reseed route, which the contract excludes.

The page renders that contract with Scalar's standalone browser bundle from `@scalar/api-reference` (MIT), pinned exactly in `package.json` (`1.72.2`, published 2026-09-29) and copied unmodified from `node_modules` by `npm run assemble`, with its licence notice at `/scalar/LICENSE.txt`. Nothing is loaded from a CDN. Assembled sizes: `scalar/standalone.js` 4,359,078 bytes (about 1.26 MB gzip, 0.94 MB brotli; Static Assets compress it), `openapi/v1.json` 147,427 bytes, and the page, its two small scripts and the licence about 4.6 KB together.

It runs under the site CSP from `public/_headers` unchanged; no `/scalar/*` relaxation is needed:

- No inline script. `scalar/before.js` and `scalar/config.js` are files; `config.js` calls `Scalar.createApiReference` with the URL and options.
- `config.js` turns off everything that would load from another origin: Scalar's font CDN (`withDefaultFonts: false`; the page uses system fonts), telemetry, the AI agent and MCP. It also hides the links that would hand the reference to Scalar's services: the developer toolbar (dashboard and registry links) and, with `hideClientButton: true`, the "Open API Client" button, which opens this contract in Scalar's hosted client at `client.scalar.com`, whose requests go through Scalar's proxy. It sets no proxy and no plugin URLs. Two kinds of off-site link remain, and neither carries API data: Scalar's credit to its home page ("Powered by Scalar" in the sidebar, "Powered By Scalar.com" in the "Test Request" panel), and, on a response's status code in that panel, MDN's page for the status, which no option turns off.
- The bundle auto-mounts a second, default-configured reference, font CDN included, on any element with the id `api-reference`, so the page mounts on `keyloop-api-reference` instead.
- The bundle's Zod copy probes for `eval` support with `Function("")`, which `script-src 'self'` blocks and reports as a violation even though the probe catches the error. `before.js` first sets Zod's `jitless` option through its global configuration object (`globalThis.__zod_globalConfig`, which the bundle reads), so Zod skips the probe and its generated parsers.

The last two rely on how this Scalar version is built. Before changing the pinned version, rerun the browser check below; if a newer bundle ignored either, the page would still work, but the browser would report blocked font requests or the `eval` probe, and the check fails.

The contract declares no servers, so `config.js` sets this origin as the only server. "Test Request" and the curl examples therefore target this site directly: anonymous reads work, and writes need the Access session, which the browser sends as the `CF_Authorization` cookie after signing in at `/auth/login` in the same browser. The local check (below) confirmed both the request target and the cookie.

**Local check.** The edge tests check the assembly, the page and configuration, and, in Miniflare's real Static Assets pipeline, the `/scalar/v1` page with the site CSP, its scripts, the redirects and the contract. The browser check serves `build/assets` (after `npm run assemble`) through the same pipeline with `public/_headers` and a fake API, and loads `/scalar/v1` in headless Chromium in light, dark and phone layouts. ## Configuration changes and container restarts

A running container keeps the environment it was started with. The platform does not apply a new Worker configuration to it: a Worker deploy leaves the container running, and a rollout to a new image restarts it with the start options it kept from the previous start (observed on the live deployment: after enabling triage and rolling out a new image, `Triage__Enabled` stayed `false`). The Durable Object therefore owns the restart. It records a SHA-256 fingerprint of each start configuration (the image reference, internet access and every environment value, secrets included; only the digest is stored, values are never stored or logged). On the first API request that each Durable Object instance handles, it rebuilds the configuration it would start with now, reading Secrets Store once, and compares the fingerprints. If the container is running with a different fingerprint, or with none recorded (a container started before this check existed), it sends SIGTERM, waits up to 15 s for Kestrel to drain, kills it if it is still running after that and waits up to 5 s more, then starts it with the current configuration and waits up to 60 s for it to listen. A container still running after the kill fails the request with the Worker's JSON `503` (`E_API_UNAVAILABLE`) and keeps its previous fingerprint, so the next request tries the restart again; the new fingerprint is recorded only once the old container has stopped. A container already running with the recorded fingerprint is never stopped again, even if it is not yet healthy: requests wait for it instead. Requests that arrive meanwhile wait on the same restart. The Worker log records `ApiContainerRestart` with reason `configuration-changed` or `unrecorded`, and `ApiContainerStopTimeout` if the kill was needed; neither carries values. After that first check, a healthy container serves requests without rereading Secrets Store (F5). If Secrets Store cannot be read during the check while the container is healthy, the request is still served by the running container, the log records `ApiContainerConfigUnverified`, and the next request checks again. A container that is not running is never started without its secrets: the health is read again after a failed read, so a container that stopped (or went to sleep) while the read was failing is not served either, and the request gets the Worker's JSON `503` (`E_API_UNAVAILABLE`); the next request checks again and starts it with its configuration.

Every deploy replaces the Durable Object instance, so each deploy checks once:

- A changed setting (an integration switch, role list, allowlist, cap or the Access issuer) or a new `KEYLOOP_API_IMAGE`: rebuild and deploy. The first API request afterwards restarts the container with the new configuration.
- A rotated Secrets Store value (`keyloop_prod_db_url`, `keyloop_prod_ai_token`, `keyloop_prod_api_otlp_token`): the Worker cannot see the change until it checks again, so deploy again after rotating (the existing prebuilt output is enough). The first API request afterwards restarts the container with the new value. A container that sleeps (`sleepAfter` 30 minutes) and starts again also picks up the current value.
- A deploy that changes nothing the container is started with (for example SPA assets only) keeps the running container.
- A container that is not running when the check happens (asleep after 30 idle minutes) simply cold-starts with the current configuration; no `ApiContainerRestart` event is logged because nothing had to be stopped.

The first deploy of this behaviour onto an already running container restarts it once, because no fingerprint was recorded for it. The first request after a configuration restart takes the stop time (up to 20 s) plus a cold start.

## Optional API telemetry

`KEYLOOP_API_OTLP_ENABLED` defaults to `false`, and then the container receives no OTLP setting at all: ServiceDefaults registers no exporter and the API behaves as it does without telemetry (`container-env-core.json` pins this). Enabling it requires `KEYLOOP_GRAFANA_OTLP_ENDPOINT`, `KEYLOOP_GRAFANA_INSTANCE_ID` and Secrets Store secret `keyloop_prod_api_otlp_token`, a Grafana Cloud access-policy token with `metrics:write`, `logs:write` and `traces:write` for this stack only. The secret binding exists only when enabled. At container start, and only then, the Durable Object reads the token and passes:

| Variable | Value |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | The gateway base URL; the .NET SDK appends `/v1/traces`, `/v1/metrics` and `/v1/logs` |
| `OTEL_EXPORTER_OTLP_PROTOCOL` | `http/protobuf`; the .NET default is gRPC, while the gateway's `/otlp` path is an OTLP/HTTP endpoint |
| `OTEL_EXPORTER_OTLP_HEADERS` | `Authorization=Basic%20<base64(instance-id:token)>`, the W3C-baggage form of the OTEL headers list: the space is percent-encoded, and base64's `+`, `/` and `=` are legal value characters |
| `OTEL_SERVICE_NAME` | `api` |
| `OTEL_RESOURCE_ATTRIBUTES` | `service.namespace=keyloop-scheduler` |

Grafana's OTLP translation builds `job` from `service.namespace/service.name`, so every series carries `job="keyloop-scheduler/api"`, which is what the committed dashboards select and what alert preparation takes as `--api-job`. Their environment variable reads `deployment_environment_name`, which ServiceDefaults sets from `ASPNETCORE_ENVIRONMENT`, `Production` here, the dashboards' default. No `service.instance.id` is set: the singleton container's series have no `instance` label. `container-env-otlp.json` is the core profile plus exactly these variables with a fake token; `test/container.test.ts` pins it to the Worker's output, and `CloudflareContainerEnvTests` boots the API with it against a loopback OTLP receiver, checking the paths, the decoded `Authorization` header, the resource attributes, and that no log record or export contains the token or the credential.

The token is never logged, never part of a Worker response and never sent to the browser; a missing or malformed token (whitespace or a non-ASCII character) refuses the container start with a message that names only the secret. A healthy container keeps its start-time environment, so enabling or disabling takes effect at the first API request after the deploy, and a rotated token at the first API request after the next deploy, when the Durable Object restarts the container ([Configuration changes](#configuration-changes-and-container-restarts)). Export failures, such as a revoked token, are not written to the container log (the .NET SDK reports them only through its own diagnostics event source), so verify ingestion in Grafana after enabling.

Two consequences to accept with it. The notification backlog gauges query the database once per metric export interval (60 s) while an exporter is configured (ARCHITECTURE section 12.1), so Neon compute stays awake for as long as the container runs, up to its 30 idle minutes, instead of suspending after Neon's idle timeout. And `appsettings.Production.json` keeps per-request framework logs out of the console and Loki: EF Core's `Microsoft.EntityFrameworkCore.Database.Command`, the `System.Net.Http.HttpClient` handlers (four records per outgoing request, the exporter's own included) and Polly's per-attempt record are raised to `Warning`, so their warnings and errors still appear.

## Vehicle-aware booking

`KEYLOOP_VEHICLE_AWARE_REQUIREMENTS` defaults to `false`, and then the container receives no `Scheduling__*` variable, so the API runs with its Production value (`false`): the booking flow is the earlier one, and a request carrying a vehicle-aware input is refused with `422 vehicle-aware-requirements-disabled` (ADR-029). `true` adds `Scheduling__VehicleAwareRequirements=true` to the container's start environment and to its fingerprint, so the first API request after the deploy restarts the container with it ([Configuration changes](#configuration-changes-and-container-restarts)); switching it back off restarts it without the variable. The API reads the option once at startup and reports it at the public `GET /api/v1/features` (`{"vehicleAwareRequirements":true}`); a web build that includes Task 31b's vehicle step shows that step, vehicle-aware availability and the allocation explanations only while it reports `true`. It needs no secret, binding or account change. `test/fixtures/container-env-vehicle-aware.json` is the Worker's core environment with the switch on, pinned by `test/container.test.ts`; `CloudflareContainerEnvTests` boots the API with it and checks the option, `GET /api/v1/features` and a vehicle-aware availability request.

## Optional intake triage

`KEYLOOP_TRIAGE_ENABLED` defaults to `false`. Enabling it requires `KEYLOOP_TRIAGE_ACCOUNT_ID` (32 hexadecimal characters), optional `KEYLOOP_TRIAGE_GATEWAY_ID` (default `keyloop-scheduler`), and Secrets Store secret `keyloop_prod_ai_token`. The secret binding exists only when enabled. Container startup passes the corresponding `Triage__*` settings. Enabling or disabling triage takes effect at the first API request after the deploy, and a rotated token at the first API request after the next deploy ([Configuration changes](#configuration-changes-and-container-restarts)). No AI token goes to Worker responses or the SPA.

The API calls Cloudflare's native `/ai/run/@cf/cloudflare/clef-flash` endpoint through the gateway with a Workers AI Read token and log collection/caching off per request. Credits, token provisioning, gateway creation/rate limit, the first live call and public enablement are stakeholder operations. This change adds configuration and local tests only. Keep triage disabled until those steps and the LiveAi golden set are approved. See [ARCHITECTURE §8.10](../../docs/ARCHITECTURE.md#810-booking-intake-triage).

Enabling triage also binds private R2 bucket `keyloop-scheduler-triage` (override with `KEYLOOP_TRIAGE_BUCKET`) as `TRIAGE_IMAGES`, configures hourly expiration cleanup, and supplies `Triage__Model=@cf/cloudflare/clef-flash`, `Triage__ImagesEnabled=true` and `Triage__ImageStoreUrl=http://triage-media.internal` to the Container. The outbound relay is reachable only from the Container hook; it is not a public route and requires no S3 credentials. Keep bucket public access disabled. The Cloudflare build configuration includes the bucket binding; provision the selected bucket before deployment if it does not already exist. Uploads expire after one hour; reads deny expired objects immediately, and hourly cleanup physically deletes abandoned objects. This does not create persistent booking attachments. `npm run validate:build:integrations` fails if the hourly cron trigger is missing, and the edge tests run the Worker's scheduled export against Miniflare R2.

**REQUIRES USER CONFIRMATION:** when provisioning the bucket, add an object lifecycle rule that deletes keys under `triage/` one day after upload (`cf r2 bucket lifecycle update`; an account operation). It backstops the sweep: disabling triage removes the R2 binding and the cron trigger, so photos uploaded shortly before would otherwise stay in the bucket. Uploads require Access sign-in and the Admin or ServiceAdvisor role (ADR-027) but have no global byte quota (ARCHITECTURE §11.1), so also watch the bucket's storage usage (an account usage notification, where available, or a periodic check).

## Access login and API roles (Task 27)

This checklist describes deploy-time operator work, all subject to stakeholder confirmation. Task 27 creates no Access applications/policies and performs no account calls. The evidence and rejected alternatives are in [ADR-027](../../docs/ADR-027.md).

1. Confirm the Zero Trust team domain and the canonical HTTPS issuer.
